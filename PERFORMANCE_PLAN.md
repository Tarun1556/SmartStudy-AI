# StudyAI Performance Plan

Findings from a full read-through of the backend (`backend/app/**`), frontend
(`frontend/src/pages/Upload.tsx`, `LectureDetail.tsx`, `lib/api/hooks.ts`), and
`docker-compose.yml` before any code was changed. Stack confirmed: FastAPI +
sync SQLAlchemy 2.0 (psycopg3) + Postgres/pgvector, Gemini/OpenAI/Anthropic
LLM providers behind a `mock`-fallback abstraction, `sentence-transformers`
embeddings behind the same fallback pattern, FastAPI `BackgroundTasks` (no
Celery/Redis) for document processing, React + TanStack Query on the frontend.

## Bottleneck table

| Area | Current behavior | Bottleneck | Proposed fix | Expected impact |
|------|------------------|------------|--------------|-----------------|
| Retrieval (RAG core) | `services/search/search_hybrid` semantic branch pulls up to 200 `SearchDocument` rows (full `content` text + embedding) per course from Postgres, then computes cosine similarity **in Python** for every row before sorting. | pgvector is installed but never used for the actual nearest-neighbor search — no `ORDER BY embedding <=> :q LIMIT k`, no index. Cost grows linearly with corpus size and ships full row content over the wire just to score it. | Use pgvector's `<=>` operator with `ORDER BY ... LIMIT` (DB-side ANN) when running on Postgres; keep the existing Python loop as the SQLite/test fallback (tests run on SQLite with Vector monkey-patched to JSON, so both paths must keep working). | Retrieval becomes O(log n) via index instead of O(n) in Python; less data transferred; scales past demo-sized corpora. |
| Vector indexes | `search_documents.embedding` and `topics.embedding` are `pgvector.Vector(384)` columns with **no index** (`init_db` only creates the extensions). | Even a native `<=>` query would sequential-scan without an index. | Create an `ivfflat` (cosine ops) index on both columns in `init_db`, guarded so it's skipped on SQLite and skipped gracefully if the table is still empty (ivfflat needs `ANALYZE`-able data; created lazily is fine for a portfolio-scale dataset). | DB-side similarity search actually benefits from the fix above instead of falling back to a scan. |
| `POST /api/ask` (RAG answer endpoint) | For each of the (up to 8) retrieved chunks, re-runs `db.query(Lecture).filter(Lecture.id == ...).first()` even though `search_hybrid` already resolved and cached the same lecture internally. | Up to 8 redundant round-trips per question, on top of the ones `search_hybrid` already made. | Reuse the `lecture_title`/`lecture_number` fields `search_hybrid` already returns instead of re-querying. | Removes ~8 DB round trips from the hottest user-facing endpoint (every chat question). |
| `services/search._lecture_cache` | Module-level **global dict**, never invalidated, that opens a brand-new `SessionLocal()` and queries `Lecture` for every uncached id, on every worker/request. | Correctness bug (renamed lecture titles go stale for the life of the process) + unnecessary second DB session per search result instead of reusing the session already passed into `search_hybrid`. | Drop the ad-hoc cache; batch-fetch the lectures needed for a result set in one `WHERE id IN (...)` query using the existing `db` session. | Fixes a staleness bug and removes N extra sessions/connections per search call. |
| `services/topics.recalculate_topic_stats` | For **every topic** in the course, re-runs `db.query(Lecture).filter(course_id==...).all()` (identical result each time) and a separate `TopicMention` query, then `find_related_topics` re-scans all other topics with embeddings and recomputes cosine similarity in Python — O(T²) with repeated identical Lecture queries. | Redundant identical query executed T times; O(T²) Python similarity work. | Hoist the course's lecture count out of the loop (computed once); this is a small, safe change. (Full O(T²)→pgvector ANN rewrite of `find_related_topics` is left for a later pass — topic counts are small at portfolio scale, so it's noted but not prioritized.) | Removes T-1 redundant identical queries per study-guide/processing run. |
| `quiz.generate_quiz` | For each of up to 30 topics, runs a separate `TopicMention` query (`ORDER BY confidence LIMIT 3`). | Up to 30 sequential round trips to build one quiz. | Batch with a single query (window function or `IN` + Python grouping/limit) since result sets here are small enough to sort client-side safely. | Cuts quiz generation from ~30 queries to 1-2. |
| `topics.py` routes (`get_topic_detail`, `get_topic_evidence`) and `services/topics.get_topic_timeline` | Loop over mentions/lectures and issue one `Lecture` query per row. | N+1 on topic detail/evidence/timeline pages. | Batch-fetch lectures with `WHERE id IN (...)` once, build a dict, look up in the loop. | Turns N+1 into 2 queries for these endpoints. |
| Background job reliability | `process_lecture_job` runs via FastAPI `BackgroundTasks` (in-process thread pool). If the process restarts (crash, `--reload`, redeploy) mid-job, the `ProcessingJob` row is left at `status="processing"` forever with no way for the user to retry. | No stale-job detection, no retry path — a killed worker permanently strands a lecture as "processing". | On startup, sweep `ProcessingJob` rows stuck in `queued`/`processing` and mark them `failed` with a clear "processing was interrupted, please retry" message; add `POST /api/lectures/{id}/retry` that re-queues a failed job idempotently. | Matches the desired architecture in the brief ("if a job fails... allow retry... do not leave it permanently stuck"). |
| Frontend: upload progress dialog | `Upload.tsx`: `useLectureStatus(created?.job_id ? null : null, 1500)` — the ternary always evaluates to `null` regardless of `created`, so the live-status query is permanently `enabled: false`. | The "Processing document…" dialog shown right after upload never polls; users see a frozen 0% bar for the entire processing duration even though the backend is actively working and `/status` is polled correctly elsewhere (`LectureDetail.tsx` does it right). | Pass the real lecture id (`created?.lecture_id ?? null`) so the existing polling hook activates. | Fixes a real, visible "is this stuck?" UX bug with a one-line change — the single highest-leverage frontend fix found. |
| Observability | No request-timing middleware; no phase-level timing in the RAG path (`ask.py`) or background job beyond coarse `progress` percentages already stored on `ProcessingJob`. | Can't currently measure P95 API latency or see where RAG time is spent (embed vs. retrieve vs. LLM) without adding logging. | Add a lightweight ASGI timing middleware that logs method/path/status/duration, and wrap the ask.py RAG stages (embed → retrieve → LLM) with timing logs. No new dependency. | Enables the before/after measurements this plan requires, and gives an interview-ready "here's how I'd debug latency" story. |
| Error surfacing | Routes generally raise `HTTPException` with clean messages; `process_lecture_job` already catches and stores `str(e)[:1000]` server-side rather than a raw traceback reaching the client. No global exception handler exists, so an unhandled exception in a route would fall through to FastAPI's default response. | Low risk today (no raw tracebacks observed reaching clients in the code read), but there's no safety net for an unexpected exception. | Add a minimal global exception handler that logs the real exception and returns a generic `{"detail": "Internal error, please retry."}` 500, so nothing added later can accidentally leak internals. | Defense in depth for "never expose raw Python exceptions" requirement. |

## Explicitly NOT doing (and why)

- **Celery/Redis** — `BackgroundTasks` is adequate at this project's scale (single-process demo app); the real reliability gap is stale-job recovery + retry, which doesn't require a broker. Revisit only if concurrent multi-worker deployment is a real requirement.
- **Streaming LLM responses** — would require reworking `ask.py`'s response model and the frontend chat UI's rendering; out of scope per the brief ("if it requires a major architectural rewrite, do not implement now").
- **LangChain** — the direct-HTTP provider abstraction already in `services/llm` is simpler to reason about and debug than a framework layer would be for 3 providers.
- **Rewriting `find_related_topics`/topic similarity to pgvector ANN** — real inefficiency (O(T²)), but topic counts per course are small in this app's domain (tens, not thousands), so the risk of touching topic-merging logic outweighs the measurable benefit right now. Flagged above instead of changed.
- **Caching LLM answers** — question text is user-specific and often unique; caching risks staleness/privacy for a negligible hit rate. The embedding/LLM provider singletons are already cached at process level (`get_embedding_provider`, `get_llm_provider`, `get_settings`), which is the safe, real caching win already in place.

## Order of implementation

P0 (stability/correctness): fix `_lecture_cache` + `ask.py` N+1, fix the Upload.tsx polling bug, add stale-job sweep + retry endpoint.
P1 (latency): pgvector-native retrieval + index, quiz/topics N+1 batching, `recalculate_topic_stats` redundant-query fix, timing middleware + RAG phase logging.
P2 (proof/testing/docs): unit tests for the changed retrieval/N+1 code paths and job retry, README updates with before/after numbers.
